# The Corridor Harness

A Python script that runs the AER Connect Corridor Acceptance Test Series as the agent, and reports precisely what happened. Spec T1, 13 September 2026, as amended by Spec T2, 14 September 2026, Spec T3, 15 September 2026, and Specs T5 and T6, 17 September 2026. The Series it runs is *AER Connect Corridor Acceptance Test Series before Sale, version 1.2, 17 September 2026*: sixty-three tests, A1 to H7.

**This repository is the harness's home.** The copy under `aer-connector` `tools/harness` is retired. Changes arrive here by pull request, never by a commit straight to `main`.

Two laws (Spec T1 §1). **The harness is the agent, not a judge.** It speaks to the corridor exactly as Claude does: MCP over HTTPS at `https://mcppro.aeredium.io/mcp`, under an agent's own OAuth consent, saying the words the Owner's Guide gives. It holds no key, no rail and no rule of its own. **A failure is evidence, not a verdict.** When a test does not come out as the Series expects, the report carries what was sent, what came back word for word, who answered, and where the truth can be read. The harness never paraphrases an answer and never guesses at a cause.

## What it needs

The Mac's own `python3`, which is Python 3.9.6, and nothing else: the standard library only (`urllib.request`, `json`, `hashlib`, `secrets`, `http.server`). There is no `requests`, no `requirements.txt` and nothing to install (Spec T1 §2 and §10 as amended by Bear on 13 September 2026). It also runs unchanged on Python 3.12.

## The files

- `corridor_harness.py` — the harness: the OAuth road, the MCP session, the chain reader and decoders, the sentence matcher, the classifier, the runner and the report.
- `corridor_consent.py` — the harness's own customer and its consent, by software (Spec T21, 26 September 2026): the sign-up and sign-in with the software passkey of `aer360_passkey.py`, the authorize road read without a listener, the consent's stages, the answer book held against the series' figures, the token exchange, and every refusal in the connector's words.
- `tools/harness_seat.sh` — the operator's one command: seats the harness's own customer on the connector's box as a Solo trial, by customer id, through `psql -v`. Never run by the harness.
- `aer360_estate_road.py` — the estate's payee road, written once and shared (Spec T23, 2 October 2026): `POST /v1/payees`, the promote, the roster pressing `approve` in T12's order until the count is met, `GET /v1/payees` the judge — the estate harness's S6 body lifted word for word, called by S6 for Northwind and Contoso and by Pathfinder's S11 for the wallet of the agent it has just created. Everything else of the estate's payment road Pathfinder reuses as `aer360_harness.py`'s own methods, by import.
- `series.py` — every test of the Series as data: id, rule, the Series' own text, the words said to Claude, the action, the expected kind, the expected sentence, the pause text. The Owner's Guide §10 table is transcribed here.
- `tables.py` — every address the harness may ever send, pinned verbatim with the page each was read from; and, since Spec P1d, the rehearsal's pins: the public RPC it reads a receipt from, the harness's own sandbox agent (its consent label, its platform account id, its wallet's address), the names of the two credential files it reads outside the repository, the platform's roads and the rehearsal's figures. No file of this repository holds a bearer, a credential or a key.
- `tests/` — the unit tests; `tests/fixtures/series-1.2.md` is the Series document, *AER Connect Corridor Acceptance Test Series before Sale, version 1.2, 17 September 2026*, amended on 14 September 2026 for A4, A5 and A6 (Spec T2) and on 15 September 2026 for A4 again (Spec T3), and otherwise byte for byte, so the tests can prove the ids against it without reaching into anybody's Downloads folder. The two amendment lines and those three paragraphs are the only difference, and a test proves that every other paragraph is still the document's own, in the document's order. Version 1.2 itself names no tester, so Spec T5's amendment of 17 September 2026 is no longer a patch on the fixture: it is the document's own wording (Spec T6).

## Running it

```
python3 corridor_harness.py --tester alice --series A B C
```

- `--series` takes any of `A B C D E F H`, default all. Series G is Albert's on the boxes and is printed in the report for a person.
- `--from D7` resumes at a test id. Series A still runs first, because nothing that moves money is sent until Series A has passed in the same run.
- `--dry` prints every call the harness would make, without connecting and without a token.
- `--consent trader` (or `payer`, `payer_nogas`) runs only the consent for one agent — by software, as the harness's own customer, with no link and no wait (Spec T21) — then calls `initialize`, `tools/list` and `aerconnect_my_agent`, and prints the agent it connected as, its pact and policy hash from `wallet_status`, and a note if the agent's role is not the one this label is for or its wallet is on a chain the product does not offer. A run consents by itself every label the run file names whose token is missing, so `--consent` is only for consenting one label again.
- `--stage2` includes E3, the Stage 2 crossing on Ethereum. Without it E3 is reported as skipped.
- `--run-file`, `--issuer`, `--out`, `--crossing-wait` override the defaults below.

The harness prints one line per test as it goes, plainly enough for a screen reader, for example:

```
D2 — pass — Uniswap v3 on Arbitrum — approval 0x…, multicall(deadline) 0x…, fee 0.000000993827160506 WETH to 0xabd0…, 0.0019 WETH arrived
```

and prints the report path at the end.

## The run file

`~/.corridor-harness/harness_run.json`, written on first use for the owner to complete. It carries no secrets: for each tester, the agent labels (`trader`, `payer`, and optionally `payer_nogas` for C8), the owner's listed address, and the list scope chosen at B4; and for each chain, a public RPC endpoint the harness may read from and the token contracts whose balances it reads for the report. Those token addresses are read targets, never destinations. Both testers may be in one file; the harness runs one tester at a time.

The run file is yours and stays on your machine; it names your testers and is never committed. Never commit it, and never name a real tester in a public place.

## The consent

Since Spec T21 (26 September 2026) the harness consents its own agents: it is its own customer, born once, seated once by the operator, and every consent is walked by software — no browser, no link, no listener, no hand. Bear, on being asked to open a consent link himself: "The whole idea about a harness is that it does it all by itself." Before it, the harness printed `Consent link for alice-trader: …` and waited on a loopback listener for a person; the consent opened by hand never reached it, and Series A stopped at A2. The road is read from the connector's code (`routes/auth.ts`, `routes/oauth.ts`, `routes/consent.ts`, `routes/guards.ts`, `services/session.ts`, `services/webauthn.ts`, `services/billing.ts`, `http.ts`), and `corridor_consent.py` names the file beside each call it makes.

**The harness is its own customer, born once.** A tester's first run signs the harness up with a software passkey from `aer360_passkey.py`, used as it is — `rp.id` from the server's options, the origin the issuer from the run file — under the display name `<tester> (harness)`, the address `harness+<tester>@aeredium.io` (the tester's name is confined to `[a-z0-9-]+`, because it is the local part) and the country `AU`. It stores the passkey at `~/.corridor-harness/<tester>/passkey.json` and the customer's id at `~/.corridor-harness/<tester>/customer.json`, both mode 600, and prints one line: *signed up as the harness's own customer <id>; seat it with tools/harness_seat.sh <id>*. Every later run signs in with the stored passkey. The sign count is saved to the file BEFORE an assertion is sent and never resent on a retry (a fresh step-up per press), because the connector refuses a counter that does not advance as a cloned passkey. There is no `--fresh`: a new tester name in the run file is the deliberate new customer, and a customer once born is never abandoned by the harness on its own.

**The seat is granted once, on the box, by the operator — by customer id, never by email, never by the harness, never by the desk's page.** The connector holds no administration key, so there is no admin road to seat a customer, and the harness will not drive the payment desk's page. Bear runs, on his Mac, as the birth scripts are run:

```
bash tools/harness_seat.sh <customer-id>
```

It speaks to the estate box over ssh (`ec2-user@3.231.26.5`, `sudo … bash -s`) and to the connector's Postgres there through `psql -v customer_id=<id>` — the id read back as `:'customer_id'`, never interpolated, every statement fed to psql on standard input, because that is the one road psql's lexer interpolates a variable on (a `-c` string goes to the server verbatim) — with `DATABASE_URL` from `/etc/aer-connector/aer-connector.env` on the box, never printed. The environment file is read by key — `DATABASE_URL`, `CONNECTOR_PRICE_SOLO_MONTHLY_CENTS`, `CONNECTOR_TRIAL_DAYS` — and never sourced, because a systemd value is unquoted and a secret with a space in it is not a line a shell may run. It reads the customer row by id and refuses unless the email matches `^harness\+[a-z0-9-]+@aeredium\.io$` exactly; refuses a customer holding an active (paid) row, and any second live row; then, in one transaction, upserts the ONE live subscription row (`subscriptions_one_live`) as the desk's webhook sets a Solo trial, and writes the zero-cent ledger line the webhook writes:

```sql
BEGIN;
INSERT INTO subscriptions (customer_id, plan, package, state, price_cents, current_period_end)
VALUES (:'customer_id'::uuid, 'monthly', 'solo', 'trialing', :'price_cents'::int,
        now() + (:'trial_days'::int + :'grace_days'::int) * interval '1 day')
ON CONFLICT (customer_id) WHERE state IN ('pending', 'trialing', 'active')
DO UPDATE SET plan = EXCLUDED.plan, package = EXCLUDED.package, state = EXCLUDED.state, price_cents = EXCLUDED.price_cents,
              current_period_end = EXCLUDED.current_period_end, updated_at = now()
  WHERE subscriptions.state <> 'active'
RETURNING customer_id, package, plan, state, price_cents, to_char(current_period_end AT TIME ZONE 'UTC', 'YYYY-MM-DD HH24:MI:SS UTC');
INSERT INTO ledger_entries (customer_id, kind, amount_cents, idempotency_key, detail)
SELECT s.customer_id, 'subscription_trial_started', 0,
       'harness:' || :'customer_id' || ':' || to_char(now() AT TIME ZONE 'UTC', 'YYYY-MM-DD'),
       jsonb_build_object('subscriptionId', s.id, 'externalSubscriptionId', NULL, 'trialDays', :'trial_days'::int,
                          'trialEndsAt', to_char((now() + :'trial_days'::int * interval '1 day') AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.MS"Z"'),
                          'seatedBy', 'tools/harness_seat.sh')
FROM subscriptions s
WHERE s.customer_id = :'customer_id'::uuid AND s.state = 'trialing'
ON CONFLICT (idempotency_key) DO NOTHING;
COMMIT;
```

`price_cents` is Solo's monthly figure as the box configures it (`CONNECTOR_PRICE_SOLO_MONTHLY_CENTS`, 4900 unless the box says otherwise); `trial_days` is `CONNECTOR_TRIAL_DAYS` (30 unless the box says otherwise) and `grace_days` the webhook's 3, so the period ends thirty-three days out; the desk's handles (`checkout_session_id`, `external_subscription_id`) stay null; the idempotency key `harness:<customer-id>:<date>` makes a second run the same day write nothing twice. It never writes `state active`, never touches `aap_account_id`, `funding_address` or any agent row, and prints what it seated: the customer id, the package, the plan, the state, the price and the period end. Solo seats three agents; the run file's three labels fill it, and an agent the series would create beyond it is refused by the platform in the connector's words and reported as such.

**The consent is walked by software, for every label, with no listener.** A run consents every label the run file names (`trader`, `payer`, `payer_nogas` where it is named) whose token is missing or is refused by the first call that uses it; `--consent <label>` consents that one label again on demand. For a label: sign in with the stored passkey (a cookie jar with `secure` and `sameSite lax` as the connector sets them; `x-aer-csrf` from `/verify`); build the authorize URL exactly as before (PKCE S256, `state`, the registered loopback `redirect_uri` — the connector matches any loopback port, and no port is bound; the client id stays in `~/.corridor-harness/client.json`); `GET` it WITHOUT following redirects and read the consent id from `Location`; `GET /v1/consent/:id?connect=1`, which is the page's "Connect a different agent" pressed for it, so the harness never meets "You are already connected". If the stage is `pay`, the seat sentence. If an agent named `<tester>-<label>` is listed with a `connectionId`, `POST /finish {connectionId, rank: the role's defaultRank}`; listed without one, `POST /finish {agentId}` (Spec 35's first connection); not listed, a step-up, `POST /agent` with the answer book, then `POST /finish {connectionId: the receipt's}`. `AGENT_ALREADY_CONNECTED` is never met, because the list says which press to make. The code and the state are parsed out of `redirectTo`, the state checked, the code exchanged at `/token`, and the tokens stored in `~/.corridor-harness/<tester>-<label>.json`, mode 600, exactly as before, with the customer id, the agent id and the road beside them. Each consent prints one line: *consented <tester>-<label> as the harness's own customer with its stored passkey; agent <id>, rank <label>; funding wallet <address>; tokens stored*. The wire sequence as walked, with each road's status, for a Trader created on a seated customer:

```
POST /v1/auth/signin/options 200 (or signup/options and signup/verify, the first time)
POST /v1/auth/signin/verify  200
GET  /authorize              302  Location: /consent?request=<id>
GET  /v1/consent/<id>?connect=1  200  stage agent
POST /v1/auth/stepup/options 200
POST /v1/consent/<id>/agent  200  the receipt, with connection.id
POST /v1/consent/<id>/finish 200  redirectTo, carrying code and state
POST /token                  200  the tokens
```

**The answer book is the harness's, per role, and the series already assume it.** Only `maxTxPerDay`, `assets` and `rank` are the role's own, read from the payload's `roles[]`; the four the page leaves for the person are the book's, pinned in `corridor_consent.py` beside the figures Series C expects:

| Answer | Trader | Payer and payer_nogas | Where the series say it |
|---|---|---|---|
| `perTxUsd` | 20 | 20 | C4 "(per transaction is 20)"; H3 restores the Payer to 20 |
| `dailyUsd` | 100 | 100 | H2 restores the Trader to 100 |
| `holdAboveUsd` | 50 | 50 | C5 restores the Payer, D13 the Trader, to 50 |
| `maxTxPerDay` | the role's own | the role's own | — (a role stating none is refused rather than filed as zero) |

| `assets` | the role's own | the role's own | — |
| `counterpartiesScope` | `agent` | the run file's `payer_list_scope` | B4's choice, made in the run file |
| `counterparties` | the eight lines of B3, `tables.TRADER_LIST_B3` (see below) | `[listed_address]` | B3's list and B4's line, both written at consent |

`series.py` is not touched: the book reads the series' figures out of the restore pauses `series.py` already carries (*set 'per trade' back to 20 dollars*) and stops the run where the two disagree, naming both, so the book is held against the series rather than being a second copy. So B4's listing is done at consent, and the series' B4 reads the list off `aerconnect_my_agent`'s compiled document (`scope.counterparties_allowed`) and passes when the address stands, asking for no save; where it does not stand, B4 pauses as before. **The Trader's list is B3's list at consent (Spec T22, 27 September 2026).** The corridor harness's Series A of 26 September as tester `bear` (run `2026-09-26-215325-bear`) had A5 refused by MCP Police — *"This agent's destination list is empty: its owner has listed nobody yet, so it may pay nobody."* — because Spec T21 named the Trader's counterparties as the payload's `questionnaire.venues`, the payload names venues by name, and the book filed `counterparties: []` rather than a venue word the access platform would refuse at pact propose. The list the Series wants was already pinned: `tables.py`'s `TRADER_LIST_B3`, eight venue keys in B3's order — Uniswap v3 SwapRouter02 on Ethereum and Arbitrum (one address), Uniswap on Base, PancakeSwap v3 SmartRouter on Ethereum, Arbitrum and Base, Circle CCTP TokenMessengerV2, Tether USDT0 on Ethereum and Arbitrum — the order of `series.py`'s `B3_LINES`, and D5 trades against PancakeSwap on Arbitrum, one of the eight. So `answer_book("trader", …)` files `counterparties` as those eight addresses under `counterpartiesScope: agent` (an EVM address is an address on every declared chain, which is what the connector's form check asks), and a Trader may trade from its first consent; the consent record at `~/.corridor-harness/<tester>-<label>.json` carries `counterparties`, the addresses filed, so the harness can read what it filed (a hand-over files none and claims none). Should the connector refuse an address, the consent fails in the connector's words as before. **B3 reads what stands before it waits.** B3's pause tells the person the eight lines stand from consent, to open Set limits for the Trader, read the list against the eight lines the harness prints, change nothing and press Enter — nothing is saved. Where the Trader's consent record carries `counterparties` equal to the eight, the harness reads the hash once after the press and, where it did not move, reads the Trader's compiled document off `aerconnect_my_agent` as B4 reads the Payer's (`scope.counterparties_allowed`): the record decides whether to read, and the platform decides the pass. Where the document lists the eight (case-insensitive on the hex, order ignored) B3 passes with *the list stood from consent (eight lines, filed <consented_at>); nothing was saved and the hash did not move (before <hash>, after <hash>)*, the platform's list and both hashes as the evidence; where it lists anything else B3 fails with *the consent record says the eight lines were filed, but the platform's compiled document lists <n> entr(y/ies): <list>; the list does not stand.*, the same evidence; where the hash did move, it passes with today's sentence. Where the record carries no `counterparties` (a Trader consented before Spec T22, or handed over) or another list, nothing changes: the person is told so beside the eight lines — *This Trader's consent record carries no such list, so the eight lines do not stand from consent: write them, save, and the hash must move.* — and the hash must move or B3 fails or skips as before; a hash that does not move with no such reading is never a pass. B8 still exercises the mirror's refresh (Rule 9). A standing agent is never re-consented and a pact's list changes only through Set limits on the account page, so a Trader consented before this change (`bear-trader`) keeps its empty list until B3 is done once by hand, or the run file names a fresh tester whose Trader is consented with the list from the start.

**The wallet address is the harness's own, and the estate harness writes it down.** `aer360_harness.py` S5, having read Harness Holdings' funding wallet, writes `~/.aer360-harness/harness-holdings/funding-wallet.json` — `{address, chain, keyId, readAt}`, no key in it. `corridor_consent.py` reads that file: `fundingAddress` is its checksummed address, a key allocated on the platform and held in the enclave (an address written in one case, EIP-55's unchecksummed form, is checksummed and used; a mixed-case address whose checksum is not its own refuses before any call); the run file's `listed_address`, when empty, is filled with the same address and written back, printed before the write; the same wallet in another spelling stands as it is; another address stops the run naming both: *the run file's listed_address <a> is not the harness's own funding wallet <b> (<path>): the harness lists only its own wallet; set listed_address to it, or leave it empty to be filled, and rerun*. Known and accepted: the Wallet registers that address as the owner root of the agents' child wallets, and a Payer's deposits land in Harness Holdings, whose S7 reads its USDC exactly before it pays — a deposit between the two reads is the estate harness's to reconcile.

**The sentences the harness can stop with**, one each, and the run stops there:

- *the harness is not seated: run tools/harness_seat.sh <customer-id> on the box, then rerun* — the read answered stage `pay`, or the create was refused `SUBSCRIPTION_REQUIRED`; *(its seat lapsed)* rides in the brackets where the standing is `lapsed` (`SUBSCRIPTION_LAPSED`). The pay stage states no date, so none is invented; the seat script prints the period end when it seats.
- *the harness's passkey counter is behind the connector's: the passkey file was not saved after a sign-in; a new tester name is a new customer* — a counter that did not advance, with the connector's own words beside it (`PASSKEY_REJECTED`: `@simplewebauthn/server`'s *Response counter value N was lower than expected M*, or the connector's own cloned-authenticator sentence).
- *no wallet address of the harness's own: run aer360_harness.py first (S5 births the funding wallet and writes it down)* — the funding-wallet file is absent.
- *the funding-wallet file at <path> carries <address>, whose checksum is not its own (<checksummed>); refused before any call*; *the passkey file at <path> cannot be read (<why>): it was not written whole. Set that folder aside, or run as a new tester name, which is a new customer* (the file is written beside itself and moved over, so this needs a hand on it).
- *the tester name '<name>' cannot name the harness's customer: it must match [a-z0-9-]+, because it is the local part of harness+<tester>@aeredium.io*.
- *the answer book and series.py disagree: <both figures>; the run stops until the two say one figure*.
- *the run file's listed_address is empty, so the Payer's list cannot be written at consent*; *the role <id> states no maxTxPerDay and the book pins none; a blank is filed as zero, which is an agent that may make no transaction at all, so nothing was filed*; *the connector lists no role <id> for the <label>; it lists <ids>*.
- Every other refusal is told as what it is, in the connector's own words: *refused: the connector refused <what> at <road> — <CODE> (<status>): <sentence> — <cause>; the answer will be the same on retry* for a 401, 402, 403, 409 or a platform's refusal relayed as 502 (the fourth agent on Solo arrives this way, in the platform's words); *malformed: the connector could not read the harness's <what> at <road> — …; the harness's question is wrong, not the connector* for a 400; *fault: the connector answered <what> at <road> with HTTP <status> …* for anything else; *unreachable: the connector could not be reached at <road>: <the transport's words>* for a connection that did not open. A refusal is never told as an outage.

**Nothing secret is printed.** `SECRET_KEYS` gains `pem`, `signature`, `cookie`, `set-cookie`, `csrfToken`, `code`, `handle` and `response`; the run folder's `evidence.jsonl` carries every wire exchange of the consent under the test id `consent`, its outcome word first (`answered`, `redirected`, `refused`, `malformed`, `fault`, `unreachable`), with those redacted to their last four characters and the cookie, the CSRF token and the code scrubbed wherever they ride, including inside `redirectTo`. Three of those words have two meanings, and the harness keeps them apart by their neighbours: an OAuth `code` beside its `state` or in the token form is a secret, a refusal's code beside its sentence is evidence and travels into the record; a WebAuthn ceremony's `response` (holding or beside `clientDataJSON`) and the `signature` inside it are secrets, a door's `response` or a ticket's `signature` is evidence. The `/token` exchange rides in the record like every other road, its code and verifier redacted. The harness never asks for, prints or stores a password or a private key of any wallet, and never reads the agent's credential; the connector holds that.

## What gates money, and what Series A costs

Nothing that moves money is sent until **A1, A2, A3, A5 and A4's native-balance check** have passed in the same run (Spec T2 §5). **A6 and A4's notes gate nothing**: they prove wording and the Wallet's own reach under Spec 49, not the corridor's judgement. The report says which of them passed, in one line under the summary, and a money test skipped by the gate names the test that held it back.

**The native-balance check gates money only when it was made and passed** (Spec T2 §5, as amended on 14 September 2026: *"a missing RPC should make anybody worry"*). A check that could not be made holds money back **exactly as a failure does**, because the report must never say money moved without the chain having been read. The gate names why it was not made — *"A4's native-balance check was not made: the run file names no RPC for arbitrum"*, or the chain's own fault quoted — and every money test skipped by it carries that sentence. **So the run file must name a readable RPC for each chain the agents are on before any money moves.** The skeleton written on first use already names one for ethereum, arbitrum and base; if a public endpoint is refusing, put one that answers in its place rather than running without.

**The fee pin.** A6 counts `fee` as a whole word, so `coffee` is not the fee. Every other pinned term is counted as it is written, wherever it sits, so `sweepTokenWithFeeAndUnwrap` and `feeRecipientAddress` are both caught. A term that opens with a digit may not begin inside a longer figure, so the fee's `5 bps` is not the `15 bps` of a slippage cap. "basis points" on its own is not counted at all: MCP Police's `check_action` schema uses the phrase for `slippage_bps` and `price_deviation_bps`, and neither is the fee.

**The chain guard.** An agent whose `wallet_status.chain` is not ethereum, arbitrum or base runs no money series at all, and the report says, for that agent: *"<label>'s wallet is on <chain>, which the product does not offer; the series runs on ethereum, arbitrum and base. Create the agent again on one of those and consent it."* The money series are C, D, E and H, whole — D4, D16 and E2 read back what the money tests did, so they are refused with the rest — and B8, which walks the corridor. Series A still runs and reports for that agent, because Series A moves nothing, and so do the owner's-road tests of Series B, which stand whatever chain the wallet is on. `--consent` says the same sentence the moment a consent lands, so a wallet on the wrong chain is found before a run is started.

**A4 reads the tokens where the Wallet puts them** (Spec T3 §2). Since Spec 49, live on 14 September 2026, `get_balances` states the token balances in `tokens.balances`, one row per asset with its `chain`, `contract`, `decimals` and `raw` figure, and says in `tokens.road` where its asset list came from. For each row the run file names, A4 compares the Wallet's `raw` with the chain's own `balanceOf` for that contract and reports agreement or the two figures; a row the run file does not name is printed as the Wallet stated it and marked not compared, because the harness reads no contract the run file did not name; a token the run file names that the Wallet does not state is read from the chain alone and said so. The `road` sentence is printed in A4's line after the balances, so what Alice's door said — *"every verified stablecoin row this door holds for arbitrum, because the pact's compiled document names no assets this door could read"* — is visible in every report. Only where `get_balances` states no tokens in either shape, Spec 49's object or a bare list, are they read from the chain alone and the Wallet's own sentence quoted in a note; where the Wallet states them and they agree with the chain, A4 is a plain pass.

**The rails line** (Spec T3 §3). A4's judgement on `wallet_status` is unchanged: a pass when the wallet's own chain is one of ethereum, arbitrum and base, and a pass with a note naming Spec 49 where no `rails` field is stated. Where the door names its rails, each is printed with its chain id, and a rail outside the three — Alice's door names `aeredium-testnet (2237)` — is printed as a note, not a failure: the door is telling the truth about itself.

**Cost.** Series A moves no money, but A5 spends **one metered `check_action` unit**: it asks MCP Police one question, the one its own role can ask, and reads the hash Police judged under. Nothing is built and nothing is submitted.

## Outcomes

- **pass** — the right kind of outcome, in the Guide's words.
- **pass with a note** — the right kind, in different words; both sentences are quoted, and F3 collects every note at the end of the report.
- **fail** — the wrong kind, a leg count or fee that does not match, a revert, or no judgment at all (a dead bearer, a door that did not answer, a relay refusal); followed by its evidence block.
- **held** — the corridor held an action the Series expected to pass; the hold's sentence is quoted. A hold the Series expected (C5, D13) is a pass.
- **skipped** — the person chose to skip, or a precondition was missing; never counted as a pass.
- **left to a person** — the Series' text and a blank line.
- **not run** — the series stopped earlier on an unexpected allow.

## The three files of a run

`~/Downloads/harness-runs/<date-time>-<tester>/`:

- `report.md` — one heading per test in Series order, the rule, the outcome and one plain sentence; a summary at the top (counts, the policy hash at the start and the end, wallet addresses and balances before and after, the total moved, the fee legs found on chain, every transaction hash); every failure's evidence block in the order Spec T1 §6 gives, ending with a where-to-read line that names the part and the rule and never a cause.
- `evidence.jsonl` — one line per call: time to the millisecond, test id, tool, the arguments exactly as sent, the answer exactly as received, the HTTP status and the round trip, with the bearer token and every receipt or ticket secret replaced by `<redacted>`.
- `chain.jsonl` — one line per transaction hash: chain, hash, block, status, `to`, the decoded call where the harness knows the selector (`approve`, `transfer`, `exactInputSingle` inside `multicall` with `sweepTokenWithFee`, `depositForBurn`, `receiveMessage`, `send`, and Curve's `exchange`), the Transfer events with from, to and amount, and the gas used.

## Safety

Nothing that moves money is sent until Series A has passed in the same run, which means A1, A2, A3, A5 and A4's native-balance check (Spec T2 §5). An agent whose wallet is on a chain the product does not offer runs no money series at all. A destination, venue contract or fee address comes from two places only: the owner's listed address in the run file, and the pinned tables, verbatim with their page. No amount is sent above the Series' own figure for that test. A refused action is never retried. `submit_transaction` is never called except with the ticket this run's `build_transaction` issued. On the first unexpected allow, an action the Series expected to be refused or held that was built or signed, the whole series stops, the report says which, and nothing further is sent until a person restarts the harness. A hold, a refusal or a chain revert never stops the run.

## Read from the code, not from memory

The tool names are the relay's: `police.<name>` and `wallet.<name>`, and the connector's own `aerconnect_my_agent` and `aerconnect_guide` (`apps/server/src/services/mcprelay.ts`). The Police tools that propose or track an assignment, `request_assignment`, `police_assignment_status` and `assignment_status`, are marked "NOT THE ROAD FOR AN AER CONNECT AGENT" (`packages/shared/src/knowledge.ts`, `ROADS`) and the harness never calls them. **MCP Police carries no tool called `can_sign`.** It said so itself: *"MCP Police carries no tool called “can_sign”. Ask for the tool list again: this server relays whatever the doors carry and never a copy of its own."* Its tools are `list_roles`, `describe_role`, `check_action`, `request_assignment`, `assignment_status` and `my_usage`. The arguments of a call are the Guide's own vocabulary (`action`, `chain`, `asset`, `amount_usd`, `to_address`, `to_asset`, `venue`, `contract_address`, `to_chain`) shaped to the door's own `inputSchema`, read whole from `tools/list` so that its `required` list and each field's description are read too: only the fields the door declares are sent, under the names it declares (the suite's door double spells Police's as `action_kind`, `asset_symbol`, `amount_usd_cents` and `child_wallet_id`), and a field the schema does not declare is named in the evidence rather than guessed. **Where a door declares more than one name for a field, the required field wins** (Spec T3 §1). MCP Police's `check_action` declares `amount_usd_cents` as required and, beside it, `amount_usd` described *"NOT ACCEPTED. Present only so an amount sent in dollars is refused rather than silently ignored"*; Alice's A5 failed on 14 September because the harness found the decoy first and sent `amount_usd: 5`, and Police refused it before judging. Now the name in the schema's `required` list is chosen; failing that, one whose description does not say NOT ACCEPTED; failing that, the first present. A door that declares only `amount_usd`, one that speaks dollars, is still obeyed. A dry run, with no schema to read, prints each field under the first name in the harness's alias table, which for the amount is `amount_usd_cents`, the name Police requires; a live call to the Wallet sends dollars under `amount_usd`, because that is the name the Wallet's own schema declares.

## The rehearsal

```
python3 corridor_harness.py rehearse --chain arbitrum [--resume <userOpHash>] [--interval 5] [--deadline 180]
```

The rehearsal walks the corridor's first sponsored operation on the tester's own road — Police, Wallet, platform, gateway, chain — as the harness's own agent, and judges the debit in dollars against the chain's receipt (Spec P1d, 24 September 2026, amended 15:45). It is a mode of its own: not part of the acceptance series, and it changes no series answer. Nothing here holds a key. The harness's wallet is a key allocated on the platform and held in the enclave, born with the harness's agent on the owner's account page; the harness only ever speaks to it through the Police and the Wallet under the agent's own OAuth consent. Three secrets are read from outside the repository and replaced by `<redacted>` wherever they appear in the output, by value and not by field name: the agent bearer from `~/.corridor-harness/harness-payer.json` (written by the consent, exactly as every agent's tokens are), the sandbox account's platform credential from `~/.corridor-harness/sandbox.env` (`AAP_ACCOUNT_KEY`, the account's own key, which the platform admits on `GET /v1/gas-account` and `GET /v1/gas/operations/{userOpHash}`), and the admin credential from `~/.aer360-harness/admin.env` (`AAP_ADMIN_BASE_URL`, `AAP_ADMIN_KEY`, exactly as Spec T14 files it). No record file is written: the pasted output is the record, and every exchange is in it — what was sent and what came back, word for word.

**What it does, in order.** It refuses a chain `tables.py` names no public RPC for (`REHEARSAL_RPC`: Arbitrum One, `https://arb1.arbitrum.io/rpc`, read only). Where no consent is stored for `harness-payer`, the consent runs — that is how the wallet comes to be the harness's — and the run stops with *fund <address> with US$0.01 or more of USDC on arbitrum, then rerun*. Before anything it reads the wallet's live key record from the Wallet (`wallet_status` → `account`: the address the key signs from, `key_id`, the chains it is delegated on, Spec 66 §1) and refuses to go on if that address differs from the one pinned in `tables.py` (`SANDBOX['wallet_address']`); it reads the sandbox account on the platform (`GET /v1/gas-account` under the account's credential), refuses if the credential's `account_id` is not the pinned one (`SANDBOX['account_id']`), and refuses to start while the ledger's recent lines hold an unreleased reservation whose operation is still `quoted` or `submitted`, naming the hash and whose wallet it is — two rehearsals never cross. While either pin is empty the run stops and says exactly what to pin, from the Wallet's and the platform's own words. Then it reads the gas account through the Wallet (`gas_account`, Spec 66 §3) and prints balance, reserved and available, and the USDC balance where the Wallet puts it (`tokens.balances`, Spec T3); below 0.01 USDC it stops with the fund sentence.

**The refusal is proved where it can be, then the gas is put on account.** At US$0.00 the send is asked once: the Police allows it — the Police refuses nothing for gas (Spec 25) — and the Wallet refuses it in U3's sentence, *Your gas account holds US$0.00. This payment needs at most US$0.33 of gas. Nothing was sent. …*, whose first figure must equal the balance read and whose second, the reservation, is printed. A ticket minted, a sentence with another first figure, or anything that left fails the rehearsal naming it; nothing is ever submitted in the refusal walk. Above zero it prints *refusal not provable at US$<balance>; skipped*. Then, below US$1.00, it credits US$5.00 through the platform's admin credit road — `POST /v1/admin/accounts/{id}/gas-account/credits`, `idempotency_key` `rehearsal-<run id>`, reason *rehearsal <run id>*, the run id being the UTC start time as `YYYYMMDD-HHMMSS` — reads the balance back through the Wallet, and fails on `deduped: true` or a rise other than US$5.00, naming the platform's answer. At US$1.00 or more nothing is credited.

**The send, as the tester's agent sends it.** Through the Police with the harness agent's bearer, then the Wallet's `build_transaction` and `submit_transaction`, shaped to the doors' own schemas as every walk of the series is: `transfer_stable`, 0.01 USDC, on the wallet's own chain, from the wallet to its own pinned address. It expects the Police's ALLOW receipt carrying `gas_account` and the Wallet's answer carrying the `userOpHash` (`execution.user_operation.user_op_hash`) and `gas_account` (Spec 66); where the Wallet's answer says the wallet was delegated first (`delegation_tx_hash`, Spec 154 §5), the delegation is an operation of the walk too and is polled and judged like the send. It then polls `GET /v1/gas/operations/{userOpHash}` under the account's credential every `--interval` seconds until `landed`; `reverted`, `expired`, `failed` or a refusal fails the rehearsal in the platform's words, and a platform that does not answer is asked again; at `--deadline` it prints the hash on a line of its own and stops with *not judged; rerun with --resume <userOpHash>*, which is not a failure. `--resume` polls and judges without sending, and finds the delegation the operation names.

**The debit is judged against the chain, in dollars (Spec 154c).** For each operation of the walk it reads from the platform the words, `reservation_usd_cents`, the four figures (`gas_usd_cents`, `service_usd_cents`, `total_usd_cents`, `margin_bps`), the recorded price (`native_usd_cents_per_ether`) and the `handleOps` transaction hash; then reads that transaction's receipt itself from the pinned public RPC (`eth_getTransactionReceipt`, standard library) and computes `gasUsed × effectiveGasPrice` at the recorded price, rounded half up as the platform rounds. It fails unless the words begin *gas and service, US$* and end *paid in advance from your gas account*; `gas_usd_cents` is within one cent of the receipt's figure; service is within one cent of gas × `margin_bps` / 10000 and at least one cent; total = gas + service exactly; total ≤ reservation; and the receipt did not revert. Then it reads the gas account through the Wallet afresh and fails unless the balance fell by exactly the sum of the walk's totals since the reading after the credit, and reserved is US$0.00, every reservation released; and it prints the USDC balance before and after, unchanged to the cent, or a finding.

**Exit codes.** 0 judged and passed; 1 failed, naming it; 2 stopped before the walk (a wallet to fund, a credential to file, a fact to pin); 3 not judged at the deadline. Every failure sentence says who answered and what they said: a platform refusal (401, 403) is told as the credential's and the same on retry, a 4xx as the harness's or the deployment's mistake, a 5xx or no answer as a fault.

**Before the first live run, in Bear's hands.** Create the harness's own owner and a Payer on AER Connect, and list the Payer's wallet address as its one destination, so the Police allows the send to itself; file `~/.aer360-harness/admin.env` (Spec T14) and `~/.corridor-harness/sandbox.env` with the sandbox account's `AAP_ACCOUNT_KEY`; run once — the consent runs, the run stops with the fund sentence and names the address to pin; pin `SANDBOX['wallet_address']` and, from the next run's reading, `SANDBOX['account_id']` in `tables.py` by pull request; fund the wallet with US$0.01 or more of USDC on Arbitrum One; then, after `deposit` has landed and Spec 154c's boot line prints the margin, rerun and paste the output back whole. Its receipt is the corridor's first sponsored operation.

The tests (`tests/test_rehearsal.py` against `tests/rehearsal_doubles.py`) run the mode against doubles of the Police, the Wallet, the platform and the chain's RPC that issue sentinel secrets, each as strict as the service it stands in for — the Police's ALLOW receipt with `gas_account` and `gas_low`, the Wallet's key record, desk, ticket and submit answer, the platform's ledger, admin credit road with `adminAuth`'s three refusals and `deduped`, `GET /v1/gas-account` with `recent_lines`, the operations read under the account's own key and 404 for another account's, the reservation and the settlement as Spec 154c computes them — and prove the whole walk from a fresh wallet; service at three cents; every failure named (the words, gas two cents off the receipt, service two cents off, total ≠ gas + service, total above the reservation, the account fallen by another figure, reserved not zero, reverted, `deduped: true`, a mismatched live address, an operation still `submitted`, a chain not in `tables.py`, a Police that refuses, a ticket minted at zero, a platform at 154 without 154c); the deadline and `--resume`; US$0.50 and US$2.00; the birth and the stops; and that no sentinel secret and no `Authorization` value appears in the output, while `tables.py` and `tests/` hold no string beginning with the platform's prefix.
