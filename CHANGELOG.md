## Spec T8 — The harness expects what the law says (20 September 2026)

From the first live run (report `aer360-harness-2026-09-20.md`) and Bear's rulings of the same morning: three lines of that run said "fail" where the estate was right or where nothing was wrong. The estate's code was read again at aeredium/AERAccounts main after PR #108 (commit dff4c9a, whose `services/onboarding.ts` is e651616's byte for byte) and at Spec 88's branch (commit 35cdc6f, not yet merged).

- `aer360_harness.py`, S11: the venue probe expects acceptance. "Unless it is stipulated explicitly in the questionnaire, it must be accepted" (Bear, 20 September 2026): the questionnaire decides policy, and a contract is an address. HTTP 201 is reported as *accepted, as the law says*, and a refusal is the finding, with the ruling quoted beside the estate's sentence; the probe's docstring carries the ruling and the day the expectation flips.
- `aer360_harness.py`, S10: the read-back is compared by content. `spoken_for` renders in the estate's own forms — `services/onboarding.ts`, the `spoken` switch, read from the code: a list entry's values in the order the estate stores them, a currency as its code, money as the dollars-and-cents sentence, a roster as the names joined by ", " — and returns None for a kind it cannot render, which S10 records as *not compared: no rendering for kind <k>*, a note and never a finding. A list is compared entry by entry, so a finding names the entry.
- `aer360_answers.py`: `as_the_estate_stores`, the shape an answer takes once written — `answers.value` is a `jsonb` column (`db/onboardingschema.ts`), and jsonb keeps an object's keys shortest first, then in byte order — so the census sent as name, email, role is spoken as `name — role — email`, which is what the estate said and what the harness's own rendering, in the order it had sent, called a disagreement.
- `aer360_harness.py`, S12: a slow call is reported and never judged. Every call over two seconds is still listed, the station passes with its numbers, and beside the invitation timings the report says *the invitation road sends the email before it answers, which is where its four seconds go* (`routes/invites.ts` awaits the dispatch before answering 201).
- `aer360_harness.py`, the report: when a previous report stands in the working folder, the closing table gains a *last run* column — the station's previous outcome and each finding's fate, closed, still open or new, matched by station and probe with the ids a run mints set aside — and the findings are listed by fate below the count. `read_report`, `find_last_report`, `finding_key` and `compare_findings` read a report this harness wrote, in Spec T7's shape or this one's. The Python confirms what was fixed.
- `aer360_harness.py`, `--dry`: unchanged in its calls; the venue line's expectation is the law's.
- Tests: the double stores an answer as jsonb does and speaks the currency as main does (JSON, the estate's finding of 20 September) with Spec 88's code behind `currency_spoken_as_code`; `refuses_venue_contract` stands in for the day the questionnaire stipulates against venue contracts, under the estate's own `ADDRESS_PROPOSAL_REFUSED`; `invite_seconds` and a shared clock make an invitation take four seconds where the live road spends them. Each of the spec's tests was red on main: the venue accepted reads as pass and a refusing double as a finding with the ruling quoted; the estate's own census line against the book's JSON entries is no finding and one moved name names its entry; a run with four-second invitations passes S12 with the sentence in the report; two reports in a folder give the closing table its last-run column with closed, still open and new; and the dry run's calls match `tests/fixtures/aer360-dry-calls.txt`, frozen from main after PR #5.
- README: the estate harness section says what the law says and what the harness now expects.
- Not touched: corridor_harness.py, series.py, tables.py, aer360_passkey.py, aer360_tables.py and the corridor's tests are not touched.

## Spec T7 — The estate harness (20 September 2026)

A Python script that walks AER 360 end to end as a founder, from Bear's ruling of 19 September 2026, read from aeredium/AERAccounts main after PR #106.

- New: `aer360_harness.py` — the runner: the invitation and sign-in ceremonies, the interviews answered from the book, the people, the wallet account, the payees, the payments, the journey; the three hats (S10 the auditor, S11 the attacker, S12 the optimizer); the dry run; the report.
- New: `aer360_passkey.py` — the software passkey: a P-256 key on the Mac's own `/usr/bin/openssl`, an attestation object in the `none` format, assertions over `authenticatorData ‖ SHA-256(clientDataJSON)`; CBOR, COSE and DER in pure Python; a pure-Python P-256 verifier and a re-statement of @simplewebauthn's checks, proven against RFC 8949 and RFC 6979.
- New: `aer360_answers.py` — the answer book: every question of the interviews with its kind and answer, the estate, the people, the money and the payments the spec decided; the live catalog's option strings byte for byte.
- New: `aer360_tables.py` — every address the estate harness may send, derived from a fixed seed and checksummed; the venue address S11 sends is read from the corridor's `tables.py` at run time.
- New: `tests/fixtures/aer360-questioncatalog.v11.ts` — the frozen version-11 catalog, copied verbatim, that the book is held against.
- New: `tests/test_aer360_*.py` — the passkey vectors, the book against the fixture, the tables, the dry run, the estate double, the founder's road against it, the three hats.
- README: the estate harness section. `.gitignore`: the report `aer360-harness-*.md` is never committed by accident.
- Not touched: corridor_harness.py, series.py, tables.py and the corridor's tests are not touched.
